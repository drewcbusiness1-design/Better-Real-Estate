# Enable actual remote push

The app/sound can be tested before this work. These server files have NOT been deployed. Do not overwrite the live website with an old website ZIP.

1. Use the Apple Developer account that owns the app identifier. In Xcode target → Signing & Capabilities → + Capability → Push Notifications. If unavailable under a Personal Team, enrolled Apple Developer Program access is needed. Confirm the registered App ID has Push Notifications enabled and rebuild provisioning. Keep the same bundle ID. Background Modes → Remote notifications is not required for the visible alerts implemented here; no silent background execution is requested.
2. Create an APNs signing key in Apple's developer account with access to this App ID. Keep the .p8 private key on the server only. Never paste it into Swift, source control, screenshots or chat. On the hosting provider configure APNS_TEAM_ID, APNS_KEY_ID, APNS_PRIVATE_KEY (the PEM .p8 contents), and APNS_TOPIC (the exact bundle ID). Both sandbox and production device registrations are supported. Debug builds use sandbox; release builds use production. These conditions assume standard development and App Store provisioning respectively; verify against the signed aps-environment entitlement.
3. In the CURRENT website repository, back up/commit existing work, then run `python3 /path/to/Server-Integration/install-push.py /path/to/website`. It only accepts exact hashes of server.js/store.js/netlify.toml from the reviewed v29.75 website baseline, and stops without changes otherwise. If it stops, integrate into current source instead: add nativePushDevices to store.js COLLECTIONS, register nativePush.cjs routes after requireAuth is defined, include the module, and add the native-push-cron function with a one-minute Netlify schedule. Existing store initialization creates the collection table when configured through its normal initialization process; review migration in staging. Do not replace a newer website with v29.75.
4. Review the patch, run `node --test Server-Integration/push-tests.cjs` in the package (or copy its tests with nativePush.cjs into a test directory), run the current website's required tests, and deploy the reviewed current website through your normal process. Scheduler calls the APNs module directly; there is no public unauthenticated dispatch HTTP endpoint. The authenticated app routes are /api/native-push/status and POST/DELETE /api/native-push/devices. Device tokens live in a separate server collection and are not included in profile settings.
5. Rebuild the app with Push capability. Sign in. Account settings → iPhone notifications → Enable push notifications. Allow the iOS prompt. The status should become 'Push notifications enabled' only after Apple registration and server device registration succeed.
6. Background/lock the phone. From another legitimate account send a NEW message after registration. Wait for the next scheduler cycle (up to about a minute). Verify banner, bark, notification tap and opt-outs. The sound respects iPhone silent/Focus/notification settings. Existing messages before device registration are not replayed. Deal notifications are also supported; other categories are not mapped yet. Revoke notifications, sign out, switch accounts and test token cleanup. Repeat with TestFlight/production credentials before release.

Scheduling is bounded per invocation and retries transient failures on the next invocation. Monitor function failures without logging device tokens or message contents. Concurrent invocation and crash recovery may duplicate an accepted delivery; no exactly-once guarantee is provided. Real sandbox/production APNs delivery and deployment are outstanding.

Apple references: https://developer.apple.com/documentation/usernotifications/registering-your-app-with-apns and https://developer.apple.com/documentation/usernotifications/unnotificationsound . No Firebase or other third-party push provider was added.


## v0.7 Live Activity addition
The updated installer also guards dealResearchJobs.js, registers nativeLiveActivities.cjs, adds nativeLiveActivities to store collections, and awaits its notifyJob hook after durable job saves. APNs Live Activity requests use the app topic plus .push-type.liveactivity and the liveactivity push type. It sends real reported progress, marks stale data, and ends completed/failed activities. Activity registration checks the authenticated user owns the job. Retry/refresh is included in the existing new push cron. None of this is deployed automatically. If v0.6 integration was already applied, the original-baseline guard intentionally stops; integrate into that current source instead of downgrading. In Xcode configure both targets and enable Push Notifications on the MAIN APP with compatible signing. No invented ActivityKit entitlement is added; NSSupportsLiveActivities is set in the app plist. Test local updates separately from remote updates while the app is suspended.
